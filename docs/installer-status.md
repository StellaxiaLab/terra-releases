# 설치기 구현 현황

기준일: 2026-10-31 · 최신 게시: `v0.6.9`

이 문서는 설치기(`terra-setup`)가 어디까지 구현되었고, 무엇을 어떤 환경에서 확인했고, 무엇이 남았는지를 적는다. 설계는 [installer-design.md](installer-design.md)에 있다. 이 문서는 **확인한 것과 확인하지 못한 것을 나누어 적는 것**을 원칙으로 한다.

> [!NOTE] 아직 시험 단계다
> `v0.6.5`부터 최신(Latest)으로 게시돼, 설치기의 기본 카탈로그 주소(`releases/latest/download/…`)가 열린다. 그래도 깨끗한 기계의 신규 설치, 실제 Linux 기기, Linux arm64는 아직 확인하지 못했고 Windows 코드 서명도 없다(아래 "아직 확인하지 못한 것").

| 원격 취득(코어·모듈 받기, 해시·서명 검증) | 구현, Windows·Linux(x86_64)에서 실제로 받아 설치함 |

| Linux arm64, 실제 Linux 기기 | **미시험** |

## 신뢰 체인

설치기는 이 저장소나 GitHub를 믿지 않는다. 설치기에 박힌 루트 공개 키와, 그 키가 인증한 릴리스 키의 서명만 믿는다.

- 서명 형식은 Ed25519, minisign 호환이다.
- 검증 순서: 인증서 → 폐기 여부 → 카탈로그 서명 → 파싱(서명 전에는 읽지 않는다) → 유효 기간 → 만료 → 롤백 하한 → 최소 설치기 버전. 하나라도 실패하면 **아무것도 받지 않는다**.
- 롤백 하한은 설치에 **성공한 뒤에만** 오른다. 받기만 하고 버린 카탈로그는 하한을 올리지 못한다.
- 카탈로그에 적힌 크기와 해시는 파일에서 직접 계산해 빌드 인덱스와 `modules.json`의 값과 맞는지 확인한 뒤 서명한다. 맞지 않으면 카탈로그를 만들지 않는다.
- 지문은 [README](../README.md)의 표를 본다.

## 구현된 기능

### 설치기(Windows · Linux)
- 부트스트랩 설치기 한 파일을 받으면 코어와 모듈은 설치기가 카탈로그를 읽어 가져온다.
- 외부에서 받은 모듈(예: 노드 GUI)은 번들에 든 모듈과 같은 설치 기록·무결성 검사·제거 경로를 쓴다. 복구와 업데이트는 캐시에서 오프라인으로 다시 놓는다.
- `terra-setup`을 인자 없이 실행하면 로컬 웹 화면이 열린다. 이전의 PowerShell 마법사와 터미널 질문 흐름은 지웠다. 옵션을 주는 비대화형 `setup` 명령은 그대로다.

### 로컬 웹 화면
- 화면은 `127.0.0.1`에만 연결되고, 1회용 토큰(주소 조각)으로 세션을 만든다. CSRF 헤더, 호스트·출처 검사, 엄격한 CSP, 단일 세션, 유휴 만료, 단일 실행 잠금을 쓴다.
- 설치 흐름: 역할 → 연결 → 모듈 → 의존성 → 옵션 → 요약 → 진행 → 완료.
- 유지관리: 검사(파일 해시 재검증), 복구, 업데이트, 수정(SSH 서버·Fleet 호스트·모듈 범위), 제거(Leaf 등록 해제 포함).
- 연결 단계(Leaf)에서 등록 방식을 고른다: Tree 주소, 이름으로 찾기, Terra ID. 계정 서비스를 쓰는 방식은 기기 승인(device flow)으로 로그인하고, 토큰과 등록 코드는 화면으로 내보내지 않는다. (0.6.8부터)
- Windows에서 `.tmod` 파일 연결을 설치·수정 때 현재 사용자 영역(HKCU)에 쓰고 제거 때 지운다. 관리자 권한이 필요 없고 사용자가 고른 기본 앱을 건드리지 않는다. (0.6.8부터)
- 설치기가 받는 모듈 릴리스는 서명되기 시작했고, 0.6.8의 카탈로그는 서명된 첫 모듈 릴리스를 가리킨다.
- 서명 실패·만료·롤백·권한 거부 같은 실패는 사람이 읽을 문구로 보여 주고, 원인 원문은 "자세한 원인"에 남긴다.

### 관리자 권한
- 화면 서버는 관리자 권한 없이 돌고, 권한이 필요한 일은 별도의 승격 도우미가 한다. 도우미는 서버를 믿지 않고 요청을 다시 검증한다(닫힌 명령 목록, 설치 경로 정책).
- **Windows**: 설치가 기계 전체(서비스·예약 작업)라서 도우미가 설치를 수행한다.
- **Linux**: 설치는 사용자 홈 안(`~/.local/share/terra`, 사용자 systemd 유닛)이라 root가 필요 없다. 화면 서버가 사용자 권한으로 설치하고, **선택 패키지(WireGuard, OpenSSH 서버) 설치만** 도우미로 보낸다.

## 확인한 것

| 환경 | 확인한 내용 |
| --- | --- |
| 게시본 외부 검증 | 로그인 없이 설치기를 받아 게시된 `.sha256`과 일치, 카탈로그 서명 검증(릴리스 키 인증서 유효 기간 포함) |
| Windows 11 (실기계) | 설치된 0.5.9를 새 설치기로 0.6.0으로 업데이트, 이후 복구, 0.6.0→0.6.1→0.6.2 업데이트, 수정(SSH 서버 끄기), 모두 화면으로 수행. 승격 도우미 연결, 서비스 재시작, 무결성 일치 확인 |
| Ubuntu 22.04 (WSL2) | 신규 설치, 파일 변조 뒤 검사·복구, 화면 API를 통한 복구·신규 설치, 제거(사용자 데이터 보존) |
| 단위·종단 시험 | 서명 체인, 변조·롤백·만료 거부, 안전한 받기·풀기, 승격 프로토콜(Windows 파이프, Linux 소켓), 화면 서버 보안 |

실기계 시험에서 발견해 고친 결함도 있다: 복구·수정이 보관된 원본과 카탈로그를 동시에 요구하던 것, 엔진이 요구하는 Tree 주소를 "나중에 등록" 화면이 비우던 것, Linux에서 도우미(root)가 사용자 설치를 `/root`에 하던 것, 엔진이 하지 않는 옵션 변경을 수정 화면이 제안하던 것.

## 알려진 한계와 문제

- **Windows 코드 서명이 없다.** 처음 실행하면 SmartScreen 경고가 뜰 수 있다. 서명 확인은 `.sha256`과 카탈로그 서명으로 한다. 정식 배포 전에 정해야 한다.
- **엔진의 `modify`는 구성 요소·모듈 범위·SSH 서버·Fleet 호스트만 바꾼다.** PATH, 자동 시작, WireGuard 모드는 설치할 때 정한다. 바꿔 달라는 요청은 "이미 같다"로 건너뛴다.
- 받는 동안 진행률이 한 자리에 머물러 보인다(코어 수백 MB). 바이트 단위 진행률은 아직 없다.
- 관리자 승인창을 3분 안에 누르지 않으면 "관리자 권한이 승인되지 않았어요"로 끝난다. 이 동작은 의도된 것이다.

## 아직 확인하지 못한 것

- 실제 Linux 기기에서의 승격 도우미(pkexec) 승인 경로
- Linux arm64
- Windows·Linux의 신규 설치(깨끗한 기계)와 Windows 제거
- 오프라인(에어갭) 설치와 미러 주소 사용
- 등록 방식 중 계정 서비스(Terra ID, 이름 찾기)를 쓰는 경로는 가짜 서비스로만 시험했다. 실제 서비스와의 실측은 아직이다.
- `.tmod` 파일 연결은 가짜 레지스트리로만 시험했다. 실제 Windows에서 더블클릭으로 여는 것은 확인하지 못했다.
- 카탈로그 정기 갱신(`renew`) 운영

## 써 보려면

시험하는 방법이다. 이 PC의 설치를 바꾸므로 시험용 기계에서 하기를 권한다. 기본 주소가 열려 있으므로 설치기를 인자 없이 실행해도(더블클릭) 화면이 열리고 카탈로그를 스스로 찾는다. 0.6.6부터 화면은 브라우저 탭이 아니라 주소창 없는 전용 창으로 열린다(Edge·Chrome이 있을 때).

1. [Releases](https://github.com/StellaxiaLab/terra-releases/releases)에서 자기 플랫폼의 `terra-setup-<타깃>`과 `.sha256`을 받아 해시를 확인한다.
2. 특정 버전의 카탈로그 주소를 직접 주고 화면을 열 수도 있다.
   ```text
   terra-setup ui --catalog https://github.com/StellaxiaLab/terra-releases/releases/download/v0.6.6/release-index.json
   ```
3. 서명만 확인하려면:
   ```text
   terra-setup catalog show --catalog <위 주소> --product terra
   ```
